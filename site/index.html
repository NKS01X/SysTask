SysTask 0.1: a process manager from /proc to the kill button

SysTask is an htop-style process manager for the Linux desktop, written in Rust and React. This post follows the data from the kernel's /proc files to a row on screen, then follows each action, such as sending a signal or pinning a process to a core, from the click to the system call.

By Nikhil Kumar Singh, 12 November 2026. Covers version 0.1.0.

What 0.1.0 does

The window has two parts. The top shows system-wide figures: total and per-core CPU, memory, swap, uptime, load average, and four history graphs (CPU, memory, disk I/O, network). Underneath is a process table you can search, sort, switch to a tree, and choose columns for. Select a process and a side panel shows its threads, open files and sockets, and lets you change its priority or the CPUs it may run on. A signal can be sent to the process or to its whole subtree.

Processes owned by root are handled through polkit, so the app itself never needs to run as root. It raises an alert, in the window and as a desktop notification, when CPU or memory stays high. Settings persist between runs.

The backend is Rust: Tauri v2, the sysinfo crate, libc, and direct reads of /proc. The interface is React 18 and TypeScript, built with Vite. Everything is Linux-specific on purpose, since it reads procfs and calls sched_setaffinity, setpriority and statvfs directly. Release 0.1.0 is packaged as a .deb and an AppImage.

How the pieces fit together

Tauri puts a Rust core and a system webview (WebKitGTK on Linux) in one process. The React app is ordinary web code served from the bundled dist folder, and it talks to Rust in two ways. The backend pushes a snapshot event to the page on every refresh. The page calls commands when the user wants something done.

Each snapshot carries a Stats block (CPU total and per core, memory, swap, uptime, load, and disk and network rates), a ProcInfo for every process, the user name SysTask runs as, and whether it is root. The commands the page can call are these.

The last three are implemented and tested in the backend but have no screen in 0.1.0. They are listed here because the API surface is part of the design.

Where the numbers come from

A process manager is mostly a careful reader of text files. The kernel exposes process and system state under /proc, and SysTask combines two sources: the sysinfo crate for the broad strokes, and its own parsers for what sysinfo does not give it.

Parsing /proc/<pid>/stat

The stat file is one line of space-separated fields. The catch is field 2, the command name, which sits in parentheses and may itself contain spaces and parentheses. A program called my (weird) name breaks any parser that splits on whitespace from the start of the line. SysTask finds the last closing parenthesis and parses everything after it, which is safe because no later field can contain one.

The unit test feeds it exactly that awkward name, and a second test checks that a truncated line returns None instead of panicking.

Turning counters into rates

The kernel reports I/O as running totals. A rate is the difference between two readings divided by the time between them. SysTask keeps the previous reading for every pid in an IoTracker. A sample is only taken if at least 0.2 seconds have passed since the last one, so a fast refresh setting cannot turn tiny deltas into noisy numbers. The subtraction saturates at zero, and a pid that vanished between samples is dropped.

Reading /proc/<pid>/io is only allowed for your own processes. For everything else the read fails, the process gets no rate, and the table shows a dash rather than a misleading zero.

For the system-wide disk figure, /proc/diskstats lists partitions and virtual devices as well as disks, and counting all of them would double count. The reader keeps whole disks and skips loop, ram, dm-, zram, sr and md devices. NVMe and MMC names are handled separately, because their partitions look like nvme0n1p1 and mmcblk0p1. The filter works from names, so it is a heuristic.

One refresh, start to finish

  1. A background thread, started at launch, sleeps for the current refresh interval. The default is one second. The window offers 0.5, 1, 2 and 5 seconds, and the backend clamps whatever it receives to between 0.5 and 10 seconds.

  2. The thread locks the Monitor and calls refresh(). That refreshes CPU usage, memory and every process in sysinfo, reads /proc/<pid>/stat for each pid, updates the per-process I/O tracker, and, if at least 0.2 s has passed, re-reads the system disk and network totals.

    procs.rs: Monitor::refresh

  3. snapshot() assembles the payload. For each process it resolves the numeric user id to a name, joins the command line into one string, merges in the stat data, and computes the memory percentage. SysTask finds its own entry in the list to learn which user it runs as, and checks geteuid() for root.

  4. If the tray icon exists, its tooltip and title are set to something like CPU 12% | MEM 41%.

  5. The snapshot is serialized and emitted as the snapshot event.

    lib.rs: handle.emit("snapshot", snap)

  6. In the webview, ingest() stores it and appends to six history series (CPU, memory, disk read and write, network receive and transmit), each capped at 120 samples. If a process is selected, its CPU value also goes into a per-process series for the side panel.

This loop runs whether or not the window is visible, which is what keeps the tray tooltip current when the window is hidden. On start, the page also calls get_snapshot once so the first paint does not wait for the first tick.

From a snapshot to rows on screen

Everything between the snapshot and the table happens in the browser side, in buildRows(). It runs on every new snapshot and every keystroke in the search box. The steps are fixed: filter, sort, and optionally nest into a tree.

Filtering and sorting

The search box matches case-insensitively against name, user, command line, and the PID as text. The "My processes" checkbox keeps only rows whose user equals the user SysTask runs as. Sorting compares numbers numerically and strings with localeCompare, treats a missing value as -1, and breaks ties by PID so rows do not jump around between refreshes. The default is CPU, descending. Clicking a different numeric column starts descending, a text column starts ascending, and clicking the active column flips it.

The tree

Every process records its parent's pid, so the tree is a grouping problem. The code indexes processes by pid, groups children under their parent, takes as roots any process whose parent is missing, and walks depth-first, emitting a row with a depth for each. Collapsed nodes are kept in a set of pids, and a collapsed node simply is not walked into. Siblings are sorted with the same comparator as the flat table.

Filtering in tree mode needs one extra step. If a search matched only a deeply nested process, showing it alone would strip its context. So the code keeps every match and all of its ancestors, and expands everything while a filter is active.

Drawing thousands of rows

A busy machine can have thousands of processes, and recreating that many DOM rows every second would be slow. The table is virtualized. Rows have a fixed height of 28 px, the scroll container is given the full height of all rows so the scrollbar is honest, and only the rows inside the viewport plus 8 above and below are rendered, positioned absolutely at the right offset. When the selection moves by keyboard, the table scrolls just enough to keep the selected row visible and clear of the sticky header.

The graphs are plain SVG polylines. The CPU and memory graphs use a fixed 0 to 100 scale. The disk and network graphs scale to the highest sample currently shown, shared by both of their lines, and in every graph the newest sample sits at the right edge.

What happens when you do something

These are the actions in the app, each as the sequence of steps behind it. Where a step touches the system, the file or call is noted underneath.

Find a process

  1. Press /. The search box takes focus unless you are already typing in a field.

  2. Each keystroke re-runs buildRows() against the latest snapshot. No request goes to the backend.

  3. Matching is by substring on name, user, command line and PID. Tick "My processes" to restrict to your own.

  4. Use ↑ and ↓, PageUp and PageDown (10 rows), Home and End to move the selection. In tree mode, → expands and ← collapses the selected node. Esc leaves the search box, then clears the selection.

Inspect what a process is doing

  1. Click a row. The side panel opens and calls get_details immediately, then again every two seconds while that process stays selected.

  2. The backend checks that /proc/<pid> exists, then reads the exe and cwd symlinks.

    /proc/<pid>/exe, /proc/<pid>/cwd

  3. Threads come from the directory listing of /proc/<pid>/task, with each thread's name read from its comm file.

    /proc/<pid>/task/<tid>/comm

  4. Open files come from reading every symlink in the fd directory. All of them are counted, the first 300 are returned, and the panel says "Showing 300 of N" when there are more. Targets of the form socket:[12345] also have their inode numbers collected.

    /proc/<pid>/fd/*

  5. The Ports tab is built by matching those inodes against the socket tables. The backend parses tcp, tcp6, udp and udp6, keeps the rows whose inode column belongs to this process, decodes the address, and maps the TCP state code to a name, for example 0A to LISTEN.

    /proc/net/tcp, tcp6, udp, udp6

  6. The kernel prints addresses as little-endian hex, so 0100007F:0050 is 127.0.0.1 port 80. IPv6 addresses are four little-endian 32-bit words.

  7. Affinity is read with sched_getaffinity. If the fd directory cannot be read, which is the normal case for another user's process, the details are marked restricted and the panel says some are hidden.

Send a signal

  1. Select a process and pick a signal from the dropdown: TERM (the default), KILL, INT, HUP, STOP or CONT. Press Delete or click Send signal.

  2. A confirmation bar names the process and PID. It carries an "As root (pkexec)" checkbox that is pre-ticked when the process belongs to root and SysTask is not root.

  3. On Confirm, the page calls kill_process(pid, signal, tree, elevated).

  4. Rust first normalizes the signal name against a whitelist of those six. sigterm, SIGTERM and term all become TERM; anything else is rejected before it can reach a system call.

    procs.rs: canonical_signal

  5. Not elevated: Monitor::kill rejects pid 0, looks the pid up in sysinfo's process table (reporting "not found" if it has already exited), and calls kill_with. A result of true is success. False becomes "permission denied or process exited".

    kill(2) via sysinfo

  6. Elevated: the backend runs pkexec kill -s SIG <pids>. Polkit shows its own authentication dialog. Exit code 126 is reported as dismissed or not authorized, and 127 as a failed authentication, usually because no polkit agent is running.

    elevated.rs: run

  7. The result lands in the status bar. If an unprivileged attempt failed with an error matching permission, not permitted or denied, the bar shows a Retry as root button. It re-runs the same action with elevated set to true.

Kill a whole tree

  1. Press Shift + Delete, or click Kill tree. The confirmation bar adds "and all its children" to its message.

  2. The backend builds a map from parent pid to child pids out of the sysinfo process table, then walks it depth-first from the chosen process. Children are listed before their parent, and the walk stops at a depth of 512 as a defence against a corrupt table.

    procs.rs: Monitor::tree_pids

  3. Pid 0 and pid 1 are refused for tree kills. Signalling the whole init tree is never what anyone meant.

  4. Unprivileged, each pid is signalled individually and the results are counted. All succeeding gives "Sent SIGTERM to N processes". Some failing gives "signalled k of N processes (permission denied for the rest)". None succeeding is an error.

  5. Elevated, the full pid list is computed first and handed to a single pkexec kill call, so one authentication covers the whole tree.

Act on a root-owned process

  1. When the selected process's user is root and SysTask is not root, signals, renice and affinity changes default to elevated. The side panel notes that the change will prompt for authentication.

  2. Processes owned by other, non-root users are not auto-elevated. The first attempt fails with a permission error, and the Retry as root button takes it from there.

  3. In both cases the elevated action is a fixed program run through pkexec: kill, renice or taskset, with numeric arguments passed as a list and never through a shell.

Change priority

  1. In the side panel, set the slider, which runs from -20 to 19 and starts at the process's current nice value, and click Apply.

  2. The page calls renice(pid, nice, elevated). The backend rejects values outside -20 to 19.

  3. Unprivileged, it lists every thread id in /proc/<pid>/task and calls setpriority on each, because Linux keeps nice per thread. The first error, if any, is reported.

    setpriority(PRIO_PROCESS, tid, nice)

  4. Elevated, it runs pkexec renice -n N -p PID.

  5. Making a process nicer, meaning a higher number, normally works for your own processes. Going below its current value normally needs root, which is the case the retry button exists for.

Pin a process to specific CPUs

  1. The panel shows one checkbox per core, filled in from sched_getaffinity. Tick the cores you want, or click All, and click Apply. Apply is disabled while nothing is ticked.

  2. The page calls set_affinity(pid, cpus, elevated). The backend rejects an empty list and any index at or above CPU_SETSIZE.

  3. Unprivileged, it builds a cpu_set_t and calls sched_setaffinity once per thread id, again because affinity is a per-thread attribute.

    sched_setaffinity(tid, ...)

  4. Elevated, it runs pkexec taskset -a -c -p LIST PID, where -a applies it to every thread.

Get alerted about sustained load

  1. Alerts are on by default, with CPU and memory thresholds of 90 percent and a sustain time of 10 seconds. All three are editable under Alerts.

  2. On each snapshot, if the value is at or above its limit, a timer starts the first time it is seen. If it is still at or above the limit once the sustain time has passed, the alert fires once.

  3. Firing shows a dismissible banner (up to three at a time) and calls notify, which runs notify-send. The message names the top consumer, the process with the highest CPU for a CPU alert or the largest resident memory for a memory alert.

  4. The alert re-arms only after the value has dropped more than five points below the limit, so a reading that hovers around the threshold does not produce a stream of alerts.

Pause, refresh rate, tray and saved settings

  • Pause makes the page ignore incoming snapshots. The backend keeps sampling. Resuming calls get_snapshot so the table jumps to the present.
  • Changing the refresh rate calls set_refresh_rate, and the refresh thread picks up the new interval on its next sleep.
  • The tray icon toggles the window on left click and has Show / Hide and Quit in its menu. If the desktop has no tray, the icon is not created and closing the window really closes it, so the app cannot end up hidden with no way back.
  • Settings are saved in the webview's localStorage under systask.settings.v1: sort column and direction, visible columns, refresh rate, theme, tree mode, "My processes", graphs on or off, and alert thresholds. The default columns are Name, PID, User, CPU %, Memory, State and Command. PPID, Mem %, CPU time, Threads, Nice, Disk read and Disk write are in the column chooser.

Guard rails

A tool that sends signals needs to be hard to misuse, including by its own bugs.

  • Pid 0 is rejected twice. kill -s SIG 0 signals the caller's entire process group. The unprivileged path already checked for it, and the elevated path did not, until pull request #2 added the check inside elevated::kill so every caller is covered.
  • Pid 1 cannot be tree-killed, on either path.
  • Signal names are whitelisted, and nice values and CPU indexes are range-checked in Rust, not only in the interface.
  • Elevated commands are fixed programs with numeric arguments, passed as an argument list.
  • The webview runs under a Content Security Policy: same-origin resources only, images from the app or data URLs, inline styles, and no network connections other than IPC to the Rust side.

Tests, CI and releases

The Rust crate has 32 unit tests. Several run against the real system rather than mocks: one starts sleep 60, sends it SIGTERM through Monitor::kill, and asserts that the child exited from signal 15. Another starts a shell with two background sleeps and checks that a tree kill finds all three processes and ends the parent. Two bind a real TCP and UDP socket and expect the socket lister to find them with the right owner. The parsers have fixed-input tests, including the malformed lines. The TypeScript side has unit tests for tree building, keyboard selection, connection filtering, CSV output and the formatting helpers.

Continuous integration runs on every push to main and on pull requests, as two jobs. The frontend job installs, runs the tests and builds. The backend job installs the WebKitGTK and tray libraries, builds the frontend (the Tauri macro needs the dist folder to exist), then runs cargo clippy --all-targets and cargo test.

Releases are driven by tags. Pushing a tag that starts with v runs the release workflow, which builds on Ubuntu 22.04 with tauri-action and uploads the bundles to a draft GitHub release. The v0.1.0 run produced SysTask_0.1.0_amd64.deb (about 2.6 MB) and SysTask_0.1.0_amd64.AppImage (about 81 MB).

What it does not do yet

  • Linux only. The readers and syscalls are Linux-specific by design.
  • Full snapshots. Every refresh serializes the whole process list and sends it. There is no diffing. It is simple and fast enough at the default rate, but it is the first thing to revisit if CPU use of the monitor itself matters.
  • Tree kills use the last snapshot. The set of children is whatever the most recent refresh saw, so a process forked in the last interval is not included.
  • Other users' I/O is blank. Per-process disk rates, and some details, need permission to read the process's /proc files.
  • No sockets or filesystems screen. The backend functions exist and are tested; the interface for them is not built.
  • No close-to-tray switch. The backend command and the stored setting exist, but there is no control for it, so the default of quitting on close applies.

Install and build

On Debian or Ubuntu, install the package from the project's releases page. On other distributions, use the AppImage.

Desktop alerts use notify-send from libnotify-bin, and elevated actions need polkit with an authentication agent running. The .deb lists both as recommended packages.

To build from source you need stable Rust, Node.js 18 or newer, and the WebKitGTK development libraries.
